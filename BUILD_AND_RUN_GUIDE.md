# Meeting Intelligence Hub — Deploy Backend + Build/Run All Frontends

This walks through hosting the FastAPI backend on Render, then building and
running each of the four clients (Web, Flutter, Chrome/Firefox extension,
C++/Qt desktop) against it. It also covers what changed with the new
login/account system.

---

## 0. What changed in this update

- **C++/Qt desktop app**: added a sign-in / create-account screen and an
  account settings panel (profile, sign out, backend URL manager). Every
  API call — including file upload and CSV/PDF export — now sends the
  `Authorization: Bearer <token>` header. A saved token is reused on next
  launch; an expired/invalid token bounces you back to sign-in automatically.
- **Web frontend**: added a matching login/register screen and an account
  menu in the top bar. Fixed two things that were silently broken by the
  backend's auth requirement: the CSV/PDF "download" links (plain `<a href>`
  can't carry an auth header — they're now authenticated fetch-and-download
  buttons) and the SSE chat-streaming helper (`EventSource` can't set custom
  headers either — it now passes the token as a query param).
- **Backend**: `auth.get_current_user` now accepts the JWT via the
  `Authorization` header *or* a `?token=` query param, so SSE streaming
  endpoints can authenticate (the code already had a comment promising this;
  it wasn't actually implemented).
- **Flutter app and browser extension**: not modified in this pass — the
  Flutter app already had working login/register/settings screens I used as
  the reference for the API contract. The extension has no auth UI; see the
  note in its section below.

## 1. Deploy the backend on Render

The repo already ships a `render.yaml` Blueprint that provisions a free
Postgres database and the FastAPI web service together.

1. **Push the project to a GitHub repo** (Render deploys from a repo, not a
   local zip).
2. In the [Render dashboard](https://dashboard.render.com), click
   **New → Blueprint**, and select that repo. Render will read `render.yaml`
   at the repo root and show you a plan: a Postgres database (`mihub-db`)
   and a web service (`mihub-backend`).
3. Click **Apply**. Render provisions both and wires `DATABASE_URL` from the
   database into the web service automatically.
4. **Set the one secret Render can't generate for you**: open the
   `mihub-backend` service → **Environment**, and add:
   - `GROQ_API_KEY` — a free key from [console.groq.com](https://console.groq.com).
     Without this the app still runs, but LLM extraction/chat will fail or
     fall back depending on your `EXTRACTOR` setting.

   Everything else in `render.yaml` is already set:
   - `JWT_SECRET` — auto-generated by Render (`generateValue: true`). This
     signs every login token; if you ever manually clear it, all existing
     sessions/tokens become invalid.
   - `JWT_EXPIRE_MINUTES=10080` (7 days) — how long a login stays valid
     before the app has to sign in again.
   - `CORS_ORIGINS=*` — wide open by default so every frontend can reach it
     while you're setting things up. **Tighten this to your actual deployed
     web app origin** (e.g. `https://your-app.vercel.app`) once you know it,
     since `*` combined with credentialed requests is not something you want
     in production.
   - `EXTRACTOR=llm`, `SESSION_TTL_HOURS=24`, `PYTHON_VERSION=3.11.9`.

5. Wait for the first deploy to finish, then confirm it's alive:
   ```bash
   curl https://YOUR-SERVICE-NAME.onrender.com/health
   ```
   You should get back a JSON health payload. **Note this URL** — every
   frontend below needs it.

### Free-tier behavior to expect
- The web service spins down after ~15 minutes idle and takes ~30–60s to
  wake up on the next request (the first login/upload after idle will feel
  slow — that's Render cold-starting, not a bug).
- Free Postgres has storage/connection limits — fine for demos, not for real
  production load. Upgrade both plans if you outgrow it.

## 2. Web frontend (React + Vite)

**Location:** `web/`

### Build & run locally
```bash
cd web
npm install
```

Create `web/.env` (Vite reads `VITE_`-prefixed vars at build time):
```
VITE_API_URL=https://YOUR-SERVICE-NAME.onrender.com
```

```bash
npm run dev        # local dev server at http://localhost:5173
```

In dev mode, note that `LLMTimingBadge` (the response-time pill) calls a
relative `/api/timing/status` path, which only works through the Vite dev
proxy defined in `vite.config.js` (it rewrites `/api/*` → your local
`localhost:8000`). That's fine for local dev against a local backend; see
the production note below.

### Production build
```bash
npm run build       # outputs to web/dist
npm run preview      # optional: serve the build locally to sanity-check
```

### Deploy the build
`web/dist` is a static site — deploy it anywhere that serves static files:
Render Static Site, Vercel, Netlify, Cloudflare Pages, GitHub Pages, or an
S3 bucket. In all cases:
- Set the `VITE_API_URL` build-time env var to your Render backend URL
  before running `npm run build` (or configure it in your host's build
  settings — Vercel/Netlify/Render Static Sites all support build env vars).
- **Production gap to be aware of:** `LLMTimingBadge.jsx` still calls a
  relative `/api/timing/status` path rather than using `VITE_API_URL`. That
  proxy rewrite only exists in the Vite *dev* server — in a production
  static deploy there's nothing to rewrite `/api/*`, so that one badge will
  fail silently (it already catches its own errors and just won't show a
  time estimate). Nothing else depends on it. If you want it working in
  production, point it at `` `${import.meta.env.VITE_API_URL}/timing/status` ``
  the same way `services/api.js` does.
- Once you know your deployed web app's exact origin, go back to the
  Render backend's `CORS_ORIGINS` env var and set it to that origin instead
  of `*`.

### What to expect on first load
You'll land on a Sign In / Create Account screen before anything else loads.
Create an account (email + password, display name optional), and you're
taken straight into the upload page. Your session token is stored in
`localStorage` and reused on refresh; the account menu (top-right in the
dashboard, top-left on the upload page) lets you sign out.

## 3. C++/Qt desktop app

**Location:** `cpp-client/`

### Prerequisites

| Tool | Version | Install |
|------|---------|---------|
| CMake | ≥ 3.20 | https://cmake.org |
| Qt | 6.4+ (or Qt 5.15) | https://www.qt.io/download |
| C++ Compiler | C++20 | GCC 11+, Clang 14+, MSVC 2022 |

**Ubuntu/Debian:**
```bash
sudo apt install qt6-base-dev qt6-tools-dev cmake build-essential
```
**macOS:**
```bash
brew install qt cmake
```
**Windows:** install Qt via the [Qt Online Installer](https://www.qt.io/download-qt-installer),
selecting Qt 6.x → Desktop (MSVC 2022 64-bit or MinGW).

### Build
```bash
cd cpp-client
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . --config Release -j
```
On Windows with Qt's own CMake integration, you can instead open the folder
in Qt Creator and build from there — it auto-detects `CmakeLists.txt`.

### Run
```bash
./MeetingIntelligenceHub        # binary name/path may vary by platform;
                                 # check build/ output after the build step
```

On first launch you'll see a **Sign In / Create Account** dialog. There's a
small ⚙ gear button in the top-right of that dialog — use it if the backend
URL isn't right yet (it defaults to `http://localhost:8000`).

### Point it at your Render backend
Two ways:
1. **Before signing in:** click the ⚙ gear in the sign-in dialog, enter
   `https://YOUR-SERVICE-NAME.onrender.com`, save. It's applied immediately
   and used for the login/register call.
2. **After signing in:** click the account icon (👤) in the sidebar → the
   Account & Settings panel has a "Backend Connection" section with a URL
   field, a list of saved addresses (double-click to switch), and an
   "Apply & Reconnect" button.

The chosen URL and your login token are both saved locally (via `QSettings`)
and reused next launch — you won't need to sign in again until the token
expires (7 days by default) or you explicitly sign out.

### Packaging for distribution (optional)
- **Windows:** run `windeployqt` on the built `.exe` to bundle Qt DLLs, then
  zip the folder or wrap it with an installer tool (Inno Setup, WiX).
- **macOS:** run `macdeployqt` on the `.app` bundle to bundle frameworks,
  then optionally create a `.dmg`.
- **Linux:** use `linuxdeployqt` or ship an AppImage; alternatively document
  the `qt6-base` runtime dependency for users installing from source.

## 4. Flutter app

**Location:** `flutter-app/mihub/`

### Prerequisites
- [Flutter SDK](https://docs.flutter.dev/get-started/install) (stable
  channel; the project targets Dart SDK `>=3.0.0 <4.0.0`)
- Platform toolchains for whichever target(s) you build:
  - **Android:** Android Studio + SDK/NDK, or just `flutter doctor` to check
  - **iOS/macOS:** Xcode (macOS host required)
  - **Windows desktop:** Visual Studio 2022 with "Desktop development with C++"
  - **Linux desktop:** standard GTK build deps (`flutter doctor` will list
    what's missing)
  - **Web:** nothing extra — Flutter's web target works out of the box

Run `flutter doctor` first and resolve anything it flags before building.

### Get dependencies
```bash
cd flutter-app/mihub
flutter pub get
```

### Run in development
```bash
flutter devices          # see what's available: emulator, browser, desktop
flutter run -d chrome     # example: run as a web app
flutter run -d macos      # example: run as a native macOS app
flutter run                # picks a connected device/emulator if only one
```

### Set the backend URL
The Flutter app has an in-app **Settings screen** with a backend URL field —
no rebuild needed to point it at Render. On first run it defaults to a
placeholder LAN address; open Settings and enter:
```
https://YOUR-SERVICE-NAME.onrender.com
```
It also already has full sign-in / create-account screens wired to the same
`/auth/login`, `/auth/register`, `/auth/me` endpoints as the other clients,
so no changes were needed there for this update.

### Build release artifacts
```bash
# Android APK
flutter build apk --release
# output: build/app/outputs/flutter-apk/app-release.apk

# Android App Bundle (for Play Store)
flutter build appbundle --release

# iOS (requires macOS + Xcode, and a valid signing setup)
flutter build ios --release

# macOS desktop app
flutter build macos --release
# output: build/macos/Build/Products/Release/mihub.app

# Windows desktop app
flutter build windows --release
# output: build/windows/x64/runner/Release/

# Linux desktop app
flutter build linux --release
# output: build/linux/x64/release/bundle/

# Web (static site, same deploy story as the React app)
flutter build web --release
# output: build/web/
```

## 5. Browser extension (Chrome / Firefox)

**Location:** `extension/chrome/` and `extension/firefox/`

This extension captures meeting audio/segments and uploads transcripts to
the backend's `/upload` endpoint. **It currently has no login UI and doesn't
send an auth header** — it wasn't in scope for this pass, but you should
know this before pointing it at your now-auth-required Render backend:
`/upload` (like every other route) requires a valid JWT, so as shipped the
extension's uploads will get a `401 Unauthorized` against the updated
backend. If you want to use the extension, it needs the same kind of
login screen + bearer-token header added to `popup.js`/`background.js` that
the web and desktop clients now have — happy to build that in a follow-up
if you'd like it included.

### Load unpacked (Chrome)
1. Open `chrome://extensions`
2. Enable **Developer mode** (top-right toggle)
3. Click **Load unpacked**, select `extension/chrome/`
4. Click the extension icon → its settings panel has a backend URL field;
   set it to `https://YOUR-SERVICE-NAME.onrender.com`

### Load unpacked (Firefox)
1. Open `about:debugging#/runtime/this-firefox`
2. Click **Load Temporary Add-on…**
3. Select `extension/firefox/manifest_firefox.json`
4. Same backend URL setup via the popup as above

(Temporary add-ons in Firefox are removed when the browser restarts; for a
persistent install you'd package and sign it via Mozilla's Add-on Developer
Hub.)

## 7. Testing the whole chain end-to-end

1. Confirm the backend is up: `curl https://YOUR-SERVICE-NAME.onrender.com/health`
2. Pick one client, point it at that URL, and create an account.
3. Upload a `.txt` or `.vtt` transcript, run extraction, try the chatbot.
4. Sign out, sign back in — your sessions should still be there (they're
   scoped to your user account in Postgres, not stored per-device).
5. Open a second client (e.g. the web app after testing the desktop app),
   sign in with the *same* account, and confirm you see the same session
   history — that's the multi-client value of having real accounts instead
   of each client hitting an unauthenticated backend independently.
